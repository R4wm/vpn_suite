# vpn_suite Context and Working Guide

## Project Goal
This repo manages a personal WireGuard VPN setup with:
- a live native server currently at `r4wm@192.168.0.116`
- repeatable onboarding for Linux, Windows, and macOS clients
- encrypted client config artifacts tracked in git
- no plaintext private keys committed

## Current Priority
1. Validate native client connectivity first (no Docker dependency).
2. Implement repeatable new-client onboarding.
3. Keep secrets encrypted at rest in repo.
4. Keep docs and scripts as source of truth.

## Source of Truth Rules
- Runtime truth for now: live server `wg0` config on `192.168.0.116`.
- Repo truth for automation: scripts + `state/clients.csv` inventory + docs.
- If live server and repo diverge, reconcile deliberately and document decisions.

## Security Requirements
- Never commit plaintext private keys or plaintext client `.conf` files containing private keys.
- Store client deliverables as encrypted artifacts under `native-clients/encrypted/`.
- Use OpenSSL encryption (`aes-256-cbc`, `pbkdf2`, `salt`, high iteration count).
- Passphrase is provided by local file:
  - default: `~/.config/vpn_suite/openssl_passphrase`
  - override: `VPN_SUITE_PASSPHRASE_FILE`
- Ensure `.gitignore` blocks plaintext secret paths.

## Onboarding Standard (Fresh Machine)
Use server-generated bundle flow:
1. Run `scripts/new-client.sh` with client name/platform.
2. Script allocates next free VPN IP, generates keys, updates registry, and emits encrypted config artifact.
3. Decrypt only for import/use on target machine.
4. Verify handshake and ping to `10.8.0.1`.
5. Record activation in registry/docs.

## Networking Defaults
- VPN subnet: `10.8.0.0/24`.
- Server VPN IP: `10.8.0.1`.
- First-connect mode: split tunnel (`10.8.0.0/24`, `192.168.0.0/24`).
- Full tunnel is opt-in per client after baseline validation.

## Test Gates (must pass)
- Existing Linux client can connect and handshake.
- Fresh client onboarding works end-to-end for at least one new client.
- Repeat onboarding for multiple clients without IP collisions.
- Encryption/decryption round-trip works; wrong passphrase fails.
- Git status shows no plaintext secrets staged.

## Change Management
- Prefer additive, scriptable workflows over manual edits.
- Any key rotation/revocation must update:
  - server peer config model
  - client registry
  - encrypted artifacts
  - docs/changelog notes
- Keep commits focused:
  1. docs/state
  2. scripts/tooling
  3. encrypted artifacts

## Deferred Items
- Docker-based server/client setup is deferred until native flow is stable.
- Router port forwarding/public endpoint exposure comes after LAN validation.
